# 形式検証（TLA+）

同期処理のうち、試験では網羅困難な並行動作（複数端末、通信失敗、処理順序の交錯）を TLA+ で模型化し、TLC で全状態を検査する。

## 実行方法

```sh
node formal/run.mjs            # 全模型
node formal/run.mjs Migration  # 設定名で絞込
```

Java 11 以上が必要。初回実行時に版数固定の `tla2tools.jar`（v1.7.4、SHA-256 照合済み）を `formal/.cache/` へ取得する。CI では `.github/workflows/test.yml` の `formal` ジョブで実行する。

各模型には「現行実装」の設定と「旧実装・不採用設計」の設定がある。現行実装は全性質を満足し、旧実装・不採用設計は指定の性質に違反する必要がある。違反を検出しなくなった場合も失敗扱いとし、模型の検出能力の喪失を防止する。

## 模型一覧

| 模型 | 対象 | 性質 | 設定と期待結果 |
| --- | --- | --- | --- |
| `Auth.tla` | トークン更新・サインアウト・サインイン（`auth-service.ts`、`credential-manager.ts`） | サインアウト後のトークン非復活、トークン非混在、単一実行、更新要求の完了（活性） | `Auth` 合格 / `AuthLegacy`（世代番号なし）違反 |
| `Migration.tla` | アドオン用 Vault 変換（`migration-service.ts`）と他端末の同期 | 編集非消失、削除ファイル非復活、変換の認知（交換後に開始した同期周期が変換を検出）、変換後 Vault の非平文混入、変換完了（活性） | `Migration`（他 1 台、ファイル 2 件）合格 / `Migration3`（他 2 台、ファイル 1 件）合格 / `MigrationNoBase`（変換時点の記録なし）違反 / `MigrationLateDelete`（既知の未修正不具合）違反 / `MigrationPR43`（削除未反映・旧フォルダ即時削除）違反 / `MigrationLegacy` 違反 / `MigrationNoFollow`（0.19.2、稼働中端末）違反 / `MigrationNoFollowRestart`（0.19.2、再起動後）違反 |
| `CloudRetry.tla` | 新規作成要求の再送（`http-client.ts`、`index.ts`、`path-resolver.ts`） | 二重作成なし、他端末項目の取違えなし、要求完了（活性） | `CloudRetry`（識別子照会）合格 / `CloudRetryBlind`（単純再送）違反 / `CloudRetryName`（名前照会）違反 |
| `SyncProtocol.tla` | 比較交換なしの送信、送信後の上書き検査と修復、統合ロック（`sync-push.ts`、`overwrite-recovery.ts`、`state.ts`） | 編集非消失、静止時の収束、全端末の収束（活性）、ロック排他性 | `SyncProtocol` 合格 / `SyncProtocolNoLock`（3 端末、ロックなし）合格 / `SyncProtocolNoCheck`（上書き検査なし）違反 / `SyncProtocolLock`（ロック排他性）違反 |

## 検出事項と対応

- **認証**: 旧実装では、サインアウト中に応答した更新要求がトークンを復活させ、再サインイン後には別セッションのトークンが混在した。PR #43 の世代番号で解消済み（`tests/tests/unit/auth-refresh-race.test.ts`）。
- **Vault 変換（削除ファイル復活）**: 変換中に他端末が削除したファイルを、追従処理が無視して変換後の Vault へ復活させていた。追従処理で削除も反映するよう修正（自端末で編集済みの場合は編集を優先）。
- **Vault 変換（交換直前の送信消失）**: 移行ロック作成前に同期を開始した他端末は、追従処理の読込後にも旧フォルダへ送信可能で、旧フォルダの即時削除により編集が消失していた。旧フォルダを 1 時間保持し、その後の同期前処理で再走査・取込してから削除するよう修正。
- **Vault 変換（フォルダ交換への追従）**: 変換は Vault フォルダを新規フォルダ（新規ファイル ID）へ交換する。0.19.2 までの模型は、他端末が「変換後 Vault と版数をパス単位で比較して再同期する」と抽象化しており、端末が保持するフォルダ ID・ファイル ID を表現していなかった。実装では、稼働中の端末は旧フォルダを保持し続けて変換を検出不可能（再起動まで同期停止）、再起動後は旧フォルダのファイル ID を指すインデックスにより、変換後 Vault の各ファイルを「無関係な同名ファイル」と誤認し、変換後ファイルを「(2)」へ改名、旧フォルダの平文ファイルを Vault 内へ移動していた。模型へ端末のフォルダ保持（`bFolder`）と誤認動作（`BResyncStale`）を追加し、`MigrationNoFollow` / `MigrationNoFollowRestart` が反例を提示。変換後 Vault が交換時点で保持した内容を `conversion-base.json` へ記録し、追従端末は「変換後に削除済み」と「変換後 Vault へ未到達」を区別する（`MigrationNoBase` が記録なしの反例を提示）。他端末は集合 `Others` で表現し、3 台構成（`Migration3`）を追加。修正: 同期開始時に Vault フォルダ ID を照合し、交換検出時はインデックスを新フォルダへ再結合（`vault-folder.ts`）。加えて ID 指定の照会・移動は Vault 内のファイルのみ対象（`google-drive/index.ts`）。実コードでの検証は `tests/sim/addon-conversion.test.ts`。
- **新規作成の再送**: Drive が処理完了後に 5xx を返す場合や応答消失の場合に POST を再送し、同名項目を二重作成していた。作成要求へ無作為の識別子（appProperties）を付与し、失敗時は識別子で照会してから再送するよう修正。名前での照会は他端末の同名項目を取り違えるため不採用（`CloudRetryName` が反例を提示）。
- **同期プロトコル**: 送信前の確認と送信の間に他端末が送信すると上書きが発生するが、送信後の上書き検査と修復により編集は消失せず、全端末が収束する。統合ロック（communication.json の書込後確認）は比較交換を持たず排他でない（`SyncProtocolLock` が反例を提示）。ただしロックなしでも安全性は成立するため（`SyncProtocolNoLock`）、ロックは重複統合の抑制のみを担い、安全性はロックに依存しない。

## 模型の対象外

- 送信後、上書き検査前のアプリ強制終了、および 10 分経過後の修復断念。上書きされた版は Drive の版履歴に残存する。
- 削除・改名・フォルダ操作の同期（多端末シミュレーション `tests/sim/` が対象）。
- Vault 変換の旧フォルダ保持時間（1 時間）は、移行ロック作成前に開始した他端末の同期周期が保持時間内に終了するという前提に依存する。端末記録が自端末のみの場合は、他端末不在と判断して交換直後に削除する。
- **既知の未修正不具合**: 交換直前に旧フォルダへ遅延送信された版を、その端末が変換後 Vault へ送信し、旧フォルダの後処理前に変換後 Vault で削除した場合、後処理が旧フォルダから再取込する（`MigrationLateDelete` が反例を提示。修正時は期待結果を合格へ変更）。
- 改名、フォルダ操作、アドオン未導入端末、パスワード変更、再ロック（`tests/sim/addon-conversion.test.ts` が対象）。保証範囲の一覧は `doc/spec/verification-coverage.md`。
- クラウド上での Vault フォルダの手動改名・削除（変換以外のフォルダ交換）。
